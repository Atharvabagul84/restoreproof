# Scope and limitations

Current additions: [S3 recovery limits](../guides/s3-recovery.md#evidence-limits), [real Chisel scope](../guides/chisel-recovery.md), and [v0.4 validation status](../history/validation-v04.md). The order-API details below describe the earlier synthetic database demo, not the GoTrue/Chisel authentication journey. [Real S3 with local Chisel passed](../history/validation-aws-live.md); GitHub federation and scoped recovery-role enforcement remain unvalidated.

See [failure-drill validation](../history/validation-failure-drills.md) and [acceptance](acceptance.md) for the current milestone. [v0.2 validation](../history/validation-v02.md) preserves the historical 134-local/18-integration result for its own revision.

- One approved PostgreSQL version and bounded custom-format logical dumps. Physical backups, WAL/PITR, replication, regional recovery and large-dataset performance are outside this version.
- Every target is disposable and created by the verifier. Existing production database URLs are not accepted.
- Contracts, archives, SQL and the Docker daemon must be trusted. Docker access is privileged; this is not a hostile-code sandbox.
- The optional order API is a short-lived loopback-only test harness, not a public HTTP server. Python's standard HTTP server is intentionally used for a bounded lab, not production deployment. See the [Python documentation](https://docs.python.org/3/library/http.server.html).
- Application SQL connects as a restricted login inside the container, using container-local Unix-socket trust authentication. Per-run tokens map to tenants in memory. This does not test production passwords, TLS, OAuth, an external identity provider, token rotation, or hosted network policy.
- Application bootstrap provisions role/grant configuration separately from the logical backup, which excludes roles and strips grants on restore. It does not repair restored data, tables or row policies. HTTP routes do not accept raw SQL or a caller-selected tenant.
- The ledger is independent of the archive and records a small, closed set of known acknowledged writes. It detects exact missing or changed records within that scope. Digest matching establishes byte identity, not recorder authenticity or complete production coverage.
- The synthetic write recorder uses logical timestamps and a single client. Client crash durability, ambiguous commit acknowledgements, concurrent writers and continuous backup snapshots require additional design and validation.
- Query row order is not transaction order. Sequence values identify expected logical writes; a reordered result array is harmless. An unexpected recovered write is a closed-scope mismatch, not automatic evidence of data corruption.
- Timings include target creation, restore and selected checks, with cleanup separate. Image pulling and fixture construction occur outside that timer. Single small-fixture runs are not production RTO, MTTR or performance improvements.
- Validated drills cover phase checkpoints, an active sleeping query, overlapping runs, and two active-COPY failure paths. Positive `pg_stat_progress_copy` counters and an active COPY command precede interruption. These are uncommitted writes, not evidence of lost committed transactions. Each COPY case requires a healthy retry of the same small archive. A bounded test-only cleanup barrier waits for the real control SQL response; it does not replace restore or verification behavior.
- The private-daemon drill passed on hosted Ubuntu with its own daemon, native containerd, socket, runtime state and storage. Controlled `SIGTERM` used `live-restore=false`; the retained target was exited after restart. Verification and cleanup were INCOMPLETE during the outage, followed by successful ownership-scoped recovery. This supports controlled API-loss handling, not uninterrupted workload operation. See the successful run (pre-release CI run 37517902305).
- No drill restarts the user's Docker Desktop or stops the runner's original daemon. Abrupt crashes, host power loss and live-restore data-plane continuity are outside the demonstrated fault model. Multiple daemons on one host are an experimental Docker configuration, used here only on a disposable runner; see [failure-drill boundaries](failure-drills.md).
- Daemon failure or host loss can prevent cleanup. Such uncertainty must remain INCOMPLETE; saved run IDs support later ownership-scoped cleanup.
- Reports can contain values returned by user-defined SQL. Use synthetic data for demonstrations and review evidence before sharing. The bundled examples do not contain production data or persisted authentication tokens.
